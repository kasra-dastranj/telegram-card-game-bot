# انتشار تصاویر نبرد، Claim، Deck و Easy — ۱۸ اکتبر ۲۰۲۶

[PR شمارهٔ ۶](https://github.com/kasra-dastranj/telegram-card-game-bot/pull/6) بازبینی، تأیید و ادغام شد. کد سیستم محلی با main هماهنگ است و بستهٔ CI نسخهٔ نهایی روی VPS فعال شد. نسخهٔ قبلی، [انتشار محدودیت بازی هم‌زمان](RELEASE_20261017_SINGLE_ACTIVE_GAME.md) بود.

## تغییرات منتشرشده

- **تصاویر نبرد:** معرفی زمین و قوانین snapshot در پیوی هر دو بازیکن Quick و Deck؛ نتیجهٔ تصویری با نام، فرم واقعی کارت، عدد نهایی، پاداش ثبت‌شده و دکمهٔ جزئیات. با تغییر زمین Quick، تصویر جدید هم نمایش داده می‌شود. شکست رندر یا ارسال تصویر به مسیر متنی برمی‌گردد و تسویهٔ بازی را تکرار نمی‌کند.
- **Deck:** پیش‌نمایش سه‌کارته، ویرایش کارت‌ها/نام و شعار برد تا ۱۲۰ نویسه. شعار انتخاب‌شده برای همان نبرد snapshot می‌شود. گزارش راندها، فرم کارت‌ها، بونس و پاداش پایدار است و پس از حذف fight نیز برای شرکت‌کنندگان در دسترس می‌ماند. مسیر بازگشت به دسته‌بندی ساخت دک و کار با دکمه‌های پیام عکس اصلاح شده است.
- **فرم پاداش:** Daily Claim در ربات و مینی‌اپ اطلاعات همان فرم واقعاً اعطاشده را نمایش می‌دهد؛ برای مثال، داشتن Legend فعال نباید پاداش Normal را با آمار Legend معرفی کند. نمایش بیوگرافی Claim و استیکر قبل/بعد ارتقا نیز اضافه شده است؛ رسانهٔ فرم دیگر جای فرم دریافتی استفاده نمی‌شود.
- **Silver Claim:** ساخت Claim ذخیره‌شده از Silver Ticket و بازکردن آن دو عملیات جدا دارند. هزینه از تنظیمات اقتصاد جاری خوانده می‌شود. رسید و کلید درخواست، مصرف دوبارهٔ منابع در درخواست تکراری را کنترل می‌کنند؛ شکست ارسال رسانه پاداش ثبت‌شده را دوباره خرج یا اعطا نمی‌کند.
- **فروشگاه:** تصویر فهرست، قیمت پیش از تأیید، موجودی و محدودیت کالا، تأیید خرید و رسید خواناتر. خرید همچنان از quote و تراکنش اقتصاد قبلی عبور می‌کند؛ مشاهدهٔ فروشگاه خرید انجام نمی‌دهد.
- **سؤال‌های Easy:** صفحهٔ مدیریت سؤال، تعریف ویژگی و فرمول جمع/تفریق بدون اجرای کد، فعال/غیرفعال‌کردن سؤال و شرط Trait/Series. هنگام شرط‌داربودن سؤال، تطابق شرط معیار اول و عدد فرمول معیار دوم است؛ کارت‌های غیرمنطبق هم بین خود مقایسه می‌شوند. فرمول و مقدار انتخاب برای بازی ثبت می‌شوند تا ویرایش ادمین نتیجهٔ همان انتخاب را عوض نکند. فهرست سؤال‌ها revision دارد و ذخیرهٔ هم‌زمانِ قدیمی با خطا رد می‌شود.
- **پنل کارت:** عددهای ویژگی Easy به‌صورت پویا از فهرست مدیریت خوانده می‌شوند؛ عددهای قبلی و Trait مستقل فرم‌های Normal/Epic/Legend هنگام ذخیره حفظ می‌شوند. ویژگی تازهٔ بدون عدد، صفر است؛ شش ویژگی پنهان قدیمی همچنان fallback قطعی قبلی دارند.

## اصلاح تکمیلی هنگام بازبینی

در تصویر نتیجهٔ Deck، تعداد راندهای برده‌شده به‌عنوان «امتیاز نهایی» نمایش داده می‌شد؛ مثلاً ۱ و ۲، در کنار معادله‌های 5 + 0 = 5 و 10 + 2 = 12. اکنون عدد بزرگ تصویر مستقیماً از total گزارش ثبت‌شده خوانده می‌شود: **۵ و ۱۲**. این اصلاح فقط نمایش را تغییر می‌دهد و برنده یا پرداخت را دوباره محاسبه نمی‌کند.

تست بازگشت ابتدا روی کد قبلی شکست خورد و پس از اصلاح موفق شد. یک fixture انقضای خرید هم به ISO تاریخ تبدیل شد تا در Python 3.12 از adapter منسوخ SQLite استفاده نکند؛ قرارداد خرید تغییر نکرد.

## آزمون‌ها و کنترل بسته

- بازاجرای محلی پس از اصلاح: **۱۲۵ تست موفق** در Python 3.12، با SQLite موقت و شبکه/Telegram غیرزنده؛ ۶۶٫۸۷ ثانیه. قبل از اصلاح نیز مجموعهٔ گسترده‌تر اجرا شد و خطای fixture بالا شناسایی شد. این بازاجرای محلی، اجرای کامل همهٔ تست‌های مخزن نیست.
- CI نهایی main در **هر دو Python 3.11 و 3.9.25: تعداد ۸۰۰ موفق / ۱ skipped**. JUnit همان run دانلود شد: هر کدام ۸۰۱ مورد، صفر failure و صفر error. frontend build، syntax JavaScript پنل، بسته‌بندی و CI gate موفق‌اند.
- manifest و hash تمام **۱۲۶ فایل runtime** بررسی شدند. هر **۱۲۲ فایل source** با blob canonical همان commit Git مقایسه شد؛ چهار فایل دیگر محصول build CI هستند.
- بستهٔ واقعی در پوشهٔ جدا و بدون assets یا frontend/public استخراج شد. **۱۵ منبع رسانه/فونت**، مجوز فونت و رندر مستقل زمین 1200×800، دک 1200×760 و فروشگاه 1200×1000 بررسی شدند. بنابراین رندر به فایل‌های ثبت‌نشدهٔ سیستم توسعه متکی نیست.
- خوانایی فارسی نمونه‌های تصویر نتیجه و فروشگاه بازبینی شد. تست مرورگر تعاملی جدید توسط مالک اجرا نشد؛ پوشش محلی این مرحله تست Python و رندر است و CI ساخت فرانت‌اند و syntax پنل را کنترل کرده است.
- Graphify به‌صورت AST-only به‌روز شد: ۳۷۱۲ گره، ۹۶۵۲ رابطه و ۲۴۱ community؛ استخراج معنایی پولی اجرا نشد.

## انتشار و حفظ داده‌ها

انتشار دستی مالک از حساب محدود telbattle-deploy و receiver نصب‌شده، با بررسی host و همان کلید اصلی محافظت‌شده انجام شد. PR همکار پس از بازبینی ادغام شد؛ اصلاح تکمیلی مالک جداگانه روی main قرار گرفت و فقط artifact موفق CI نهایی منتشر شد. workflow، bootstrap، helper مورد اعتماد و مجوز سرور تغییر نکردند.

receiver قفل مشترک `/opt/telbattle/deploy.lock`، baseline و requirements، preflight آفلاین روی کپی SQLite و عدم تغییر منطقی داده در startup را کنترل کرد؛ بکاپ سازگار گرفت و نسخهٔ فعال را عوض کرد. schema migration، restore داده، نصب dependency جدید روی VPS، اعطای منابع تست یا تغییر flagهای اقتصاد/قابلیت‌ها انجام نشد. اقتصاد جدیدِ ازقبل‌فعال و موجودی بازیکنان حفظ شدند؛ عملیات جدید Silver Claim فقط هنگام درخواست بازیکن تراکنش ثبت می‌کند.

رسید نهایی: **status=ok، internal_health=ok** و source_sha/run_id دقیقاً برابر جدول بالا. کنترل داخلی شامل هر سه سرویس، وضعیت خروج/ری‌استارت، API health، HTML پنل، API کارت/گزینه‌ها و HTML مینی‌اپ است. rollback فقط کد را برمی‌گرداند و داده‌های نوشته‌شده پس از شروع را خودکار restore نمی‌کند.

DNS، TLS و nginx در این انتشار تغییر نکردند.
