# انتشار حمله‌های گروهی و پنل کارت سفارشی — ۱۹ اکتبر ۲۰۲۶

[PR شمارهٔ ۸](https://github.com/kasra-dastranj/telegram-card-game-bot/pull/8) پس از بازبینی کد و تست، توسط مالک تأیید و ادغام شد. سیستم محلی با main هماهنگ است و artifact موفق CI همان commit روی VPS منتشر شد. نسخهٔ قبلی، [انتشار تجربهٔ بازیکن و فروش ابیلیتی](RELEASE_20261018_PLAYER_EXPERIENCE_ABILITIES.md) بود.

## تغییرات منتشرشده

### حمله‌های گروهی

- پنل مدیر بازی برای ساخت حملهٔ تک‌دشمن یا گروهِ دو تا هشت دشمن اضافه شد. دشمن می‌تواند فرم مشخص یک کارت رسمی، همان فرم با آمار مستقل NPC، یا NPC مستقل با استیکر اختصاصی باشد؛ NPC به موجودی بازیکن تبدیل نمی‌شود.
- نبردها Quick یک‌راوندی‌اند: جمع دو ویژگی انتخاب‌شده روی هر کارت پس از اثر زمین، Passive و ابیلیتی. انتخاب NPC پیش از انتخاب ویژگی بازیکن ثبت می‌شود. موجودی ابیلیتی مشترک و قفل بازی فعال رعایت می‌شوند؛ کارت سفارشی خصوصی وارد این رویداد عمومی نمی‌شود.
- عضویت همان گروه بررسی و قوانین/جریمه در پیوی نمایش داده می‌شوند. فقط تأیید صریح بازیکن، رزرو سکه/قلب و ورود را انجام می‌دهد؛ اعضای غایب یا تأییدنکرده هزینه‌ای ندارند. هر نفر فقط یک دشمن از همان حمله را می‌گیرد.
- سهم همهٔ شرکت‌کنندگان تأییدشده یکسان است. برد تیم پس از تکمیل همهٔ نبردها و اکثریت برد ثبت می‌شود؛ اکثریت قطعی باخت می‌تواند پیش از تکمیل، نتیجهٔ باخت تیم را تسویه کند. در این باخت، همهٔ شرکت‌کنندگان تأییدشده سهم یکسان جریمه دارند، از جمله کسی که نبردش هنوز کامل نشده است. حملهٔ ناتمام با نتیجهٔ نامشخص، لغو یا وقفهٔ زمان‌بندی، بدون پاداش/جریمه بسته می‌شود و رزرو/ابیلیتی طبق رسید برمی‌گردد.
- پاداش سکه، XP و فرم رسمی Normal/Epic/Legend/Rare قابل تعریف است. Rare پیش از اعلام حمله برای تمام سهم‌ها رزرو و با serial یکتا صادر می‌شود؛ مسیر صدور عادی نیز رزرو را لحاظ می‌کند. اتصال‌های خواندنی بررسی رزرو Rare در Windows به‌طور قطعی بسته می‌شوند.
- شمار شکست و خروج دائمی دشمن، برای همان گروه و شناسهٔ حمله ثبت می‌شود. انتخاب نوع، وزنی و تصادفی است و نوع قبلی پشت‌سرهم تکرار نمی‌شود. سقف روزانهٔ ورود هر حساب میان گروه‌ها مشترک است.
- job هر ۳۰ ثانیه زمان‌بندی و صف اعلان را بررسی می‌کند. تنظیم گروه تست اختیاری، پیش‌فرض خاموش، مخصوص یک شناسهٔ عددی و دارای پایان حداکثر ۲۴ساعته است. در آن گروه، حملهٔ بعدی زودتر از ۶۰ ثانیه پس از پایان قبلی ساخته نمی‌شود؛ پاداش و جریمه همچنان واقعی‌اند. دستور /chatid فقط شناسهٔ گروه را نشان می‌دهد.
- حذف کارت رسمیِ ارجاع‌شده در تعریف حمله یا حملهٔ جاری رد می‌شود تا پاداش یا دشمنِ ثبت‌شده ناقص نشود.

### پنل سادهٔ کارت سفارشی

- روند روزمره: **اتصال با توکن ← اطلاعات کارت/تصویر و پیش‌نمایش ← انتخاب گیرنده ← ساخت و تحویل**. JSON و مراحل سفارش/پرداخت از فرم روزمره حذف شدند؛ درگاه یا خرید سکه اضافه نشده است.
- Normal/Epic/Legend، چهار ویژگی، Trait دلخواه، بیوگرافی/شعار/Series، تصویر خصوصی و بخش جمع‌شوندهٔ Hidden Stats، Ability و Passive در دسترس‌اند. جست‌وجوی حساب با نام، یوزرنیم یا شناسهٔ فارسی/انگلیسی و انتخاب حداکثر ۵۰ گیرنده وجود دارد.
- ساخت، فعال‌سازی و اعطای دسترسی در یک تراکنش ثبت می‌شوند؛ درخواست نامعتبر اثر جزئی ندارد و retry همان درخواست، کارت تازه نمی‌سازد. Coin، XP، قلب و موجودی رسمی از این مسیر تغییر نمی‌کنند.
- ویرایش نسخهٔ قدیمی رد می‌شود. ویرایش کارت معلق آن را خودکار فعال نمی‌کند؛ فعال‌کردن اقدام صریح مدیر است. تحویل تعریف موجود به نفر تازه، لغو فردی، تعلیق و قطع دسترسی تصویر نیز وجود دارند.
- سابقهٔ جدید admin_managed با مبلغ/واحد خالی است؛ پرداخت verified جعل نمی‌شود. API و سابقهٔ قدیمی حفظ شده‌اند و Audit/request_key برقرارند.
- توکن در حافظهٔ صفحه است و در URL، localStorage یا sessionStorage ذخیره نمی‌شود. API علاوه بر BasicAuth بیرونی، توکن مدیریتی مستقل می‌خواهد. تحویل کارت هیچ feature flag را خودکار روشن نمی‌کند.

راهنماها: [حمله‌های گروهی](../docs/GROUP_ATTACKS_FA.md)، [پنل کارت سفارشی](../docs/CUSTOM_CARD_ADMIN_FA.md) و [قرارداد یک بازی فعال](../docs/SINGLE_ACTIVE_GAME_FA.md).

## وضعیت محتوا و فعال‌سازی

فهرست حمله‌ها در کد پیش‌فرض خالی است، نمونهٔ پیشنهادی خاموش است و گروه تست پیش‌فرض تنظیم نشده است. در این انتشار **هیچ تعریف حمله، گروه تست، کارت سفارشی، پرداخت، پاداش آزمایشی یا تغییر flag در تولید ثبت نشد**. مدیر باید محتوای واقعی را از پنل بسازد و آگاهانه فعال کند. برای زمان‌بندی تست، حداقل دو نوع حملهٔ فعال و زنده آماده کنید؛ یک نوع به‌تنهایی پشت‌سرهم تکرار نمی‌شود.

## تست و بررسی بسته

- **محلی: ۱۳۴ تست مرتبط موفق** در Python 3.12، با مدت ۹۳٫۷۷ ثانیه؛ حمله‌ها، زمان‌بندی تست، تحویل دستی و قرارداد کارت سفارشی. **۴ تست تکمیلی Rare نیز جداگانه موفق** شدند؛ ۳٫۸۱ ثانیه. SQLite موقت، شبکهٔ تست محدود و Telegram mock استفاده شد؛ اجرای کامل محلی مخزن ادعا نمی‌شود.
- **CI نهایی main: در هر دو Python 3.11 و 3.9.25، تعداد ۹۹۷ موفق / ۱ skipped.** JUnitهای همان run دانلود شدند؛ هر کدام ۹۹۸ مورد، صفر failure و صفر error. تست زندهٔ تلگرام عمداً اجرا نشده است.
- frontend build، syntax JavaScript تمام پنل‌ها، بسته‌بندی و CI gate موفق‌اند. workflow، bootstrap، helper انتشار، migrations و requirements تغییر نکرده‌اند.
- manifest/hash هر **۱۴۰ فایل runtime** بررسی شد؛ هر **۱۳۶ فایل source** با blob canonical همان commit Git تطبیق دارد. چهار فایل دیگر محصول build CI هستند.
- بسته در پوشهٔ جدا و بدون assets یا frontend/public بررسی شد: import ماژول‌های تازه از خود artifact، وجود هر دو HTML تازه/به‌روز، پیش‌فرض خالی حمله‌ها و خاموش‌بودن گروه تست، **۱۵ منبع رسانه/فونت** و مجوزها، رندر زمین/نتیجه/دک/فروشگاه/قیمت ابیلیتی و WebP استیکر موفق بودند.
- Graphify با AST-only به‌روز شد: **۴۰۲۲ گره، ۱۰۹۹۴ رابطه و ۲۵۳ community**. استخراج معنایی پولی اجرا نشد.
- بررسی مالک در این مرحله کد، API و تست‌های Python، بسته و پاسخ صفحات تولیدی بود؛ آزمون مرورگر تعاملی یا نبرد زنده توسط مالک اجرا نشد.

## انتشار و حفظ داده‌ها

انتشار دستی مالک از حساب محدود telbattle-deploy، با host verification، همان کلید اصلی محافظت‌شده و receiver نصب‌شده انجام شد. قفل مشترک `/opt/telbattle/deploy.lock`، baseline، requirements و preflight آفلاین روی کپی SQLite با عدم تغییر منطقی داده در startup کنترل شدند؛ سپس بکاپ سازگار، تعویض نسخه و شروع سرویس‌ها انجام شد.

رسید **status=ok** و **internal_health=ok** است؛ SHA/run دقیقاً برابر جدول بالا و previous_sha همان runtime قبلی‌اند. کنترل داخلی هر سه سرویس، خروج/ری‌استارت، API health، پنل، API کارت/گزینه‌ها و HTML مینی‌اپ موفق است. schema migration، نصب dependency، restore داده یا تغییر سیاست موجودی/flag اجرا نشد. job تازه فقط هنگام اجرا در namespace موجود، heartbeat/فعالیت/صف را ثبت می‌کند و انتشار، پاداش یا جریمهٔ نمونه ایجاد نمی‌کند.

rollback فقط کد را برمی‌گرداند و دادهٔ نوشته‌شده پس از شروع را خودکار restore نمی‌کند. قطع بین ارسال اعلان و ثبت تحویل ممکن است متن/استیکر را تکرار کند؛ پرداخت، جریمه و serial با رسید تراکنشی ثبت می‌شوند و بازپخش اعلان آن‌ها را تکرار نمی‌کند.
