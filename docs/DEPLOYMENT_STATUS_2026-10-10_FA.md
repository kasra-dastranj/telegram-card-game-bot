# وضعیت انتشار TelBattle — ۱۰ اکتبر ۲۰۲۶

راه‌اندازی اولیهٔ GitHub و VPS توسط صاحب پروژه انجام شده است. همکار نباید bootstrap اولیه را دوباره نصب کند، به سرور SSH بزند یا کلیدهای صاحب پروژه را بگیرد.

- PR شمارهٔ ۱ ادغام شده است؛ ابتدا شاخهٔ شخصی را با `origin/main` هماهنگ کنید.
- تست و build در GitHub اجباری‌اند؛ `main` به یک تأیید و بازبینی صاحب کد نیاز دارد.
- Environment به نام `production` فقط شاخهٔ `main` را می‌پذیرد و قبل از انتشار تأیید `kasra-dastranj` لازم است. شخصی که اجرا را شروع کرده، نمی‌تواند تأیید خودش را ثبت کند.
- secretهای اختصاصی انتشار و متغیرهای مقصد تنظیم شده‌اند. مقدار secret را دریافت، چاپ یا در فایل پروژه ثبت نکنید.
- حساب محدود `telbattle-deploy` فقط درخواست انتشار/بازگشت را پردازش می‌کند؛ shell، SCP و root عمومی در اختیار همکار نیست.
- قفل مشترک `/opt/telbattle/deploy.lock` و صف GitHub از تداخل انتشارها جلوگیری می‌کنند. انتشار دستی صاحب پروژه هم باید همین قفل و وضعیت ثبت‌شدهٔ انتشار را رعایت کند.

## هر بار که دوستت تغییری آماده کرد

۱. روی `collab/mohammadhosein-mirzanezhad` تغییر را تست، commit و push کند؛ PR به `main` بدهد و منتظر تست موفق و تأیید/ادغام صاحب پروژه بماند.

۲. پس از ادغام، با حساب خودش از GitHub → Actions → **Deploy TelBattle** → Run workflow، شاخهٔ `main` و عملیات `deploy` را انتخاب کند. از Codex هم می‌تواند بخواهد این فرمان را اجرا کند:

```powershell
gh workflow run deploy.yml --repo kasra-dastranj/telegram-card-game-bot --ref main -f operation=deploy
gh run list --repo kasra-dastranj/telegram-card-game-bot --workflow deploy.yml --limit 5
```

۳. ابتدا تست، build و بستهٔ همان commit اجرا می‌شوند؛ سپس job تولید منتظر تأیید صاحب پروژه می‌ماند. این انتظار خطای دسترسی نیست. تأیید را دور نزنید و برای ادامه از کلید root استفاده نکنید.

۴. در پایان لینک اجرای GitHub، SHA منتشرشده و receipt با `internal_health=ok` را گزارش کند. `gh run watch RUN_ID --repo kasra-dastranj/telegram-card-game-bot` وضعیت اجرا را نشان می‌دهد. گزارش دسترسی خارجی را جدا بخواند؛ مشکل DNS دامنهٔ nip.io لزوماً به معنای خرابی سرویس داخلی نیست.

۵. اگر کد به دیتابیس یا وابستگی تازه نیاز داشته باشد، انتشار ممکن است عمداً متوقف شود. مهاجرت یا نصب وابستگی تولیدی کار بازبینی‌شدهٔ صاحب پروژه است؛ workflow خودش تغییر ناشناختهٔ دیتابیس را اعمال نمی‌کند.

## نسخهٔ منتشرشده و قابلیت‌های خاموش

Traitهای مستقل و ابیلیتی یک‌بار در مسابقهٔ سه‌راندی فعال و منتشر شده‌اند. طبق تصمیم صاحب پروژه، اقتصاد و پیشرفت v2، کارت سفارشی، سفارش سفارشی، Quick Friendly و Easy با کارت سفارشی خاموش‌اند. انتشار کد به معنای فعال‌کردن این گزینه‌ها نیست. فعال‌سازی آن‌ها به تست و تصمیم بعدی محصول نیاز دارد.

اولین انتشار توسط صاحب پروژه با همان sender/receiver محدود و بستهٔ موفق CI انجام و تأیید شد. یک اجرای کامل Deploy از GitHub که همکار آغاز کند و صاحب پروژه تأیید کند، هنوز انجام نشده است؛ تنظیمات و دسترسی لازم آماده‌اند.

بازگشت نسخه هم از workflow با عملیات `rollback` و SHA کامل نسخهٔ فعال درخواست می‌شود و تأیید صاحب پروژه لازم دارد. بازگشت کد، دیتابیس را restore نمی‌کند.
