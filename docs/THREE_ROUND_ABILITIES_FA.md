# ابیلیتی‌های مسابقهٔ سه‌راوندی مینی‌اپ

این تغییر برای **نبرد با بازیکن دیگر و تمرین با ASO** است. هر بازیکن در کل مسابقه فقط **یک ابیلیتی** مصرف می‌کند؛ می‌تواند آن را تا راوند دوم یا سوم نگه دارد. انتخاب ویژگی بدون استفاده از ابیلیتی، این فرصت را برای راوند بعد حفظ می‌کند.

## ابیلیتی‌های قابل استفاده

| ابیلیتی | عملکرد در مسابقهٔ سه‌راوندی |
| --- | --- |
| مشاهده کارت حریف (`reveal_opponent`) | کارت حریف را برای مصرف‌کننده تا پایان مسابقه آشکار می‌کند. در PvP، حریف با این کار کارت تو را نمی‌بیند. |
| تغییر زمین (`reroll_arena`) | زمین متفاوتی از مجموعهٔ مجاز Mini App انتخاب می‌کند. تقویت زمین جدید از راوند جاری به بعد اعمال می‌شود؛ نتایج راوندهای قبلی حفظ می‌شوند. |
| کاهش قدرت، سرعت، هوش یا محبوبیت (`weaken_*`) | ۲ واحد از ویژگی مشخص حریف در وضعیت همین مسابقه کم می‌کند؛ مقدار زیر صفر نمی‌رود و کارت ذخیره‌شده تغییر نمی‌کند. |

کلیدها، نام‌ها و موجودی همان ابیلیتی‌های Quick هستند. خرید جداگانه لازم نیست. مصرف یک عدد در Quick، نبرد سه‌راوندی یا ASO، از همان موجودی کم می‌کند. تعریف Trait روی خود کارت در پنل مدیریت، مصرف ابیلیتی بازیکن محسوب نمی‌شود.

ابیلیتی‌های `lock_*` در مسابقهٔ سه‌راوندی نمایش داده نمی‌شوند و سرور نیز مصرفشان را رد می‌کند. قانون طبیعی استفادهٔ یک‌باره از هر ویژگی در راوندها برقرار است. ASO موجودی مصنوعی یا مصرف خودکار ابیلیتی ندارد.

## استفاده در رابط

۱. بعد از انتخاب کارت، در صفحهٔ راوند منوی «انتخاب ابیلیتی» را باز کن.
۲. پیش از ثبت ویژگی، ابیلیتی دلخواه را انتخاب کن؛ یا ویژگی را انتخاب کن و ابیلیتی را برای راوند بعد نگه دار.
۳. بعد از مصرف، نام ابیلیتی و شمارهٔ راوند مصرف نمایش داده می‌شود و انتخاب دوباره بسته می‌شود.

اگر زمین ابیلیتی را غیرفعال کند یا زمین متفاوتی برای تغییر وجود نداشته باشد، موجودی مصرف نمی‌شود. در PvP، مهلت راوند با مصرف ابیلیتی تمدید نمی‌شود. کارت حریف در پاسخ API و روی میز تا مصرف مشاهده یا پایان مسابقه مخفی می‌ماند؛ ASO نیز همین رفتار را دارد.

## قرارداد فنی و سازگاری

- سیاست مشترک در `systems/three_round_abilities.py` و تعاریف اصلی در `systems/game_mode_system.py` است. افزودن نوع اثر جدید نیازمند پیاده‌سازی اثر و آزمون در هر دو مسیر است؛ نام جدید به‌تنهایی کافی نیست.
- PvP: `POST /api/v1/three-round/matches/<request_id>/ability` با `ability_key` و `round`.
- ASO: `POST /api/v1/solo/ability` با `fight_id`، `ability_key` و `round`. وضعیت بازی از `GET /api/v1/solo/fights/<fight_id>` خوانده می‌شود؛ پاسخ `/solo/round` نیز `fight` به‌روز دارد.
- شمارهٔ راوند باید عدد صحیح همان راوند جاری باشد؛ درخواست دیررسِ راوند قبلی مصرف نمی‌شود.
- مصرف موجودی، اثر و ثبت استفاده داخل یک تراکنش SQLite با `BEGIN IMMEDIATE` انجام می‌شوند. دوبار کلیک، درخواست هم‌زمان یا شکست ذخیره‌سازی نباید باعث مصرف دوباره یا اثر ناقص شوند.
- ثبت PvP در JSON موجود `game_match_states` است. ASO از کلید خصوصی `_three_round_ability` در JSON موجود `solo_fights.arena_snapshot` استفاده می‌کند؛ این کلید از شیء زمین در پاسخ عمومی حذف می‌شود و استفاده به‌صورت `my_ability` برمی‌گردد. جدول یا ستون جدید لازم نیست.
- بازی‌های قدیمی بدون ثبت ابیلیتی، مصرف‌نشده محسوب می‌شوند. وضعیت ثبت‌شده پس از راه‌اندازی دوبارهٔ API حفظ می‌شود. بازگردانی کد، موجودی مصرف‌شده را خودکار برنمی‌گرداند.
- قوانین پاداش، XP، اقتصاد، Claim و Upgrade تغییر نکرده‌اند. تست‌ها فقط روی دیتابیس موقت انجام می‌شوند.

## بررسی و انتشار

تست‌های سرور در `tests/test_mini_three_round_api.py` شامل مصرف مشترک، مشاهدهٔ خصوصی، کاهش هر چهار ویژگی، تغییر زمین در راوند دوم و سوم، رد قفل، درخواست دیررس، رقابت هم‌زمان و rollback تراکنش هستند. تست‌های قبلی ASO نیز دوباره اجرا می‌شوند.

برای بررسی رابط با پاسخ‌های ساختگی و بدون اتصال به تولید، از داخل `frontend/game` سرور محلی را با `npm run dev -- --host 127.0.0.1` اجرا کن و در ترمینال دیگر `node scripts/qa-three-abilities.mjs` بزن. Playwright نصب‌شدهٔ پروژه و Edge روی Windows یا Chromium نصب‌شدهٔ Playwright لازم است. تصاویر بررسی در `test-results/three-abilities` ذخیره می‌شوند و وارد Git نمی‌شوند. نمایش افقی کوچک، طبق رفتار فعلی برنامه، راهنمای چرخاندن دستگاه را نشان می‌دهد.

ثبت این تغییر روی شاخهٔ همکاری آن را روی سرور فعال نمی‌کند. انتشار بعد از بازبینی، ادغام در main، موفقیت CI و آماده‌سازی اولیهٔ مسیر Actions طبق [راهنمای انتشار](DEPLOY_FROM_GITHUB_FA.md) انجام می‌شود. این تغییر ابیلیتی، migration ساختاری جدید ندارد؛ پیش‌نیاز مهاجرت Trait مربوط به تغییر قبلی در [راهنمای Trait](CARD_TRAITS_FA.md) همچنان برقرار است.
